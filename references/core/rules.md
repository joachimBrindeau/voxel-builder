# Eight rules — apply on every change

These rules are mandatory. Read this file at the start of every Voxel build, audit, or fix session — and again when in doubt. Each rule has bitten production at least once.

1. **Never guess prop names or `$$type` shapes — and regenerate the schema SSOT at the start of every run.** The offline source of truth is the committed artifact `cli/src/generated/widget-schemas.json` (generated from the widget-registration SSOT under `plugins/custom/elementor-framework/schemas/` by `wpdev elementor:codegen`, and CI-gated against drift). Run `wpdev elementor:codegen` **unconditionally as the first step of every build / migration** — one command, no "if stale" guard — then read the artifact for every EF V4 atomic widget before writing JSON. Codegen also syncs a byte-identical copy to `../../references/ef/widget-schemas.json` (drift-gated alongside the canonical one) so the plugin carries its own schema mirror; either path resolves to the same bytes. Use `wpdev elementor:schema <site> <widget> [--prop <key>]` as the live-introspection fallback only — to confirm a specific site's actually-registered shape. Either way the prop names, defaults, enums, and repeater item shapes come from the schema, never from memory. `wpdev elementor:codegen:verify <site>` is the live-site companion gate — it cross-checks the PHP runtime widget registration against the committed `widget-schemas.json`, proving the two loaders agree; run it when a site's EF version may have advanced past the committed SSOT (e.g. after a plugin update), or when `elementor:codegen --check` passes offline but a site-specific mismatch is suspected.

   **The SSOT covers PROPS, not NODE SHAPE, RESERVED-CELL envelopes, or ROW-vs-WIDGET loop scope — these silent-empty/wrong-render bugs need separate checks (see [`../ef/widgets.md`](../ef/widgets.md) §Node shape + §Reserved-cell envelopes):** (a) an EF atomic node is `{elType:'<ef-name>'}` with **NO `widgetType`** — the classic `{elType:'widget',widgetType:'ef-card'}` shape renders an empty child (now caught by the `node-shape` lint category + the import pre-write gate); (b) `_vx_loop` / `_vx_visibility` are base-class cells **skipped by the prop validator** — author the exact `{$$type:'vx-loop',value:{tag,limit,offset}}` / dtag-rule `{type:'dtag',tag,compare,arguments}` shapes with **bare** tags (no `@tags()` wrapper); (c) emptiness-gate tags need the right form (repeater → `@post(faq).count()`, relation → `@post(rel.id)`, scalar → `@post(field)`); (d) loop placement must match the repeated unit — if a single composite row references `@post(<repeater>.<subfield>)` while sibling rows are static, put `_vx_loop` on that row's `value`, not on the host `ef-card`/widget. Verify any gate tag with `\Voxel\render("@site().then(<tag>).is_not_empty().then(yes).else(no)")` on a real post before writing, and dump after mutation to assert row-level loop placement where applicable.

2. **Never hand-write `ts-*` widget JSON from memory — bind to complete, atomic reference files.** Voxel theme widgets aren't introspected by `elementor:schema`, so the canonical shape is a **golden reference fixture maintained in this skill** ([`examples/`](../../examples)) — one complete, atomic fixture per widget, capturing the full prop envelope. Read the fixture for the widget you need; adapt it. `wpdev elementor:dump <site> <ts-widget> --post <real_production_id> --json` is the way you *create or refresh* a fixture (dump the most complete production instance, commit it), not an ad-hoc per-build copy of whatever live instance happens to be nearby. If no fixture exists for a `ts-*` widget the build needs, create one from the most-complete production dump before proceeding. **Freshness gate (#20):** a fixture is valid only if it is not behind the site's installed Voxel/EF version — when the theme/plugin version moved past the fixture's captured version, refresh the fixture from a live dump before binding, or the build halts. A silent build on a stale fixture shape is forbidden.

3. **For preview cards, use `wpdev voxel:cards`** — never hand-write `_elementor_data` for the `card` role. The command produces an unwrapped `ef-card` widget with the right `_cssid` envelope, dynamic-title heading, and `custom_templates.card[]` registration.

4. **The main agent orchestrates through named subagents.** The main agent owns route selection, shared context, fan-out planning, aggregation, judgment gates, and write-once assembly; it does not perform non-trivial leaf work itself. Dispatch the matching brief under [`../subagents/`](../subagents/) for each atomic scope: one widget (`voxel-widget-builder`), one section (`voxel-layout-architect` / section audit), one plan criterion (`voxel-plan-reviewer`), one URL verifier, one schema question (`voxel-schema-detective`), one entity investigation (`voxel-curator-agent`), or one FAQ source content item (`voxel-faq-author`). See [`parallel-dispatch.md`](parallel-dispatch.md) for the full contract. **Two dispatch modes:** (a) **build mode** — each subagent emits scoped JSON/patch material, main agent assembles and writes once; (b) **read-only investigation mode** — each subagent reads source / data and reports findings, NEVER proposes a patch or writes a file. If no subagent runtime exists, read the matching brief and execute that same atomic scope inline, recording the fallback; do not collapse the whole page into one undifferentiated pass.

5. **Decide static vs dynamic per widget** based on render context — CPT templates → Voxel dynamic tags (`@post`, `@author`, `@site(loop_*)`); standalone pages → static unless explicitly bound. See [`voxel-tags.md`](../voxel/voxel-tags.md) §Static vs dynamic.

6. **Snapshot once, then prune ALL revisions — the build always targets the latest `_elementor_data`.** Elementor templates accumulate WP post revisions on every editor save — sometimes hundreds per template, each cloning the full `_elementor_data`. At the start of any non-trivial template modification, run `wpdev elementor:revisions:prune <site> --post <id>` — it snapshots the current `_elementor_data` (reversible via `wpdev elementor:revisions:restore`), then deletes every revision so you operate on the latest data only. This is unconditional, not an offer: do not ask, do not leave historical revisions in place. See [`template-resolution.md`](../voxel/template-resolution.md) §Revisions for the WP-vs-Voxel-admin distinction.

7. **Verify in a real browser after writing — screenshot + layout assertions are mandatory, not optional.** Browser work uses the **`agent-browser` CLI** through Bash. Partition representative complete/sparse/typical URLs into batches of 5-10 URL leaves, keep one isolated `--session vb-<post_id>-<n>` per URL, and run bounded waves. Each URL leaf must navigate, screenshot and inspect the PNG, scrape HTML, check console/errors, and run computed-style assertions. Lint and text grep cannot prove layout. If the browser cannot launch, mark `render-unverified`; never report a pass from curl text alone. Tool surface: [`browser.md`](../verification/browser.md); workflow: [`build.md`](../../workflows/build.md) Phase 6.

8. **Run the page-planning sub-pipeline before any non-trivial build or migration — adversarial review is mandatory, not advisory.** Every build or migration workflow invocation that touches more than a single widget MUST produce a **gated** Plan Document at `/tmp/plan-<post_id>.md` (the §2g gate is green — auto when every Critical criterion passes / carries a valid override, or operator-`APPROVED` on escalation) (Field Inventory + Widget Catalog from SSOT + Archetype Selection + Section Blueprints + adversarial review findings + reconciliation) BEFORE Phase 3 widget fan-out. The adversarial review fan-out dispatches the relevant `voxel-plan-reviewer` criteria, one concern each, in a single message — default to the full panel (`coverage` / `density` / `hierarchy` / `data-wiring` / `pattern-reuse` / `relations` / `ssot-integrity`, +`migration-preservation` when migrating); narrow it only with a stated reason. Every Critical/Improvement finding receives an outcome (`resolved` / `override: <concrete reason+evidence>` / `deferred`); an invalid (generic, evidence-less) override fails its own override-validity criterion and keeps the finding open. The gate is computed — it goes green autonomously when no open Critical remains; the operator is the exception path (escalated only when a Critical can't be auto-resolved or `--require-approval` was set). See [`page-planning.md`](../../workflows/page-planning.md) for the full §2a–§2g protocol. **The historical failure mode this rule defends against:** a data-rich CPT single template, produced via the old one-sentence "decide the widget tree top-down" instruction, ended up as an `ef-wrapper > ef-card` stub — 2 widgets — while the CPT carried its fields plus traversable relations all unsurfaced. Every plan-review criterion catches a slice of this regression.

**Audit silent-failure probes.** When auditing, also run the four mandatory detection probes for render-valid-but-wrong regressions that lint and screenshots miss — relation-loop self-traversal, CSS-token fallback drift, reindex-after-filter, unicode corruption. See [`audit.md`](../../workflows/audit.md) §Silent-failure detection probes; each emits as `suspected` with an `sme_question`.

## Success criteria — every build

The eight rules above are inputs; this checklist is the output. Every Voxel build / fix run must satisfy every checkbox before declaring done.

- [ ] A **gated** Plan Document at `/tmp/plan-<post_id>.md` exists (§2g gate green — `GATE: green (auto)` or escalated operator-`APPROVED`), produced by the page-planning §2a–§2g sub-pipeline ([`page-planning.md`](../../workflows/page-planning.md)).
- [ ] The Plan Document's §2a Field Inventory was built from `wpdev voxel:fields` + `wpdev voxel:data` on **a representative sample of real posts** (one is never enough; the data-wiring and coverage adversaries reject single-post inventories).
- [ ] The Plan Document's §2b Widget Catalog cites `cli/src/generated/widget-schemas.json` (the committed SSOT) for every EF V4 atomic widget and a `wpdev elementor:dump` source for every `ts-*` widget.
- [ ] The Plan Document's §2c Archetype Selection picked from the established catalog OR documents an exception with a pattern-reuse override justified by a peer-template comparison.
- [ ] The relevant `voxel-plan-reviewer` criteria (the full panel by default; narrowed only with a stated reason) were dispatched in a single message in §2e; their findings file lives at `/tmp/plan-review-<post_id>.md`.
- [ ] Every Critical and Improvement finding in §2e carries a `resolved:` / `override:<concrete reason>` / `deferred:` outcome line in §2f. No silent ignores.
- [ ] The §2g gate went green — `GATE: green (auto)` (every Critical criterion `pass`/valid-override) or an escalated operator `APPROVED` — before Phase 3 fan-out started.
- [ ] The orchestrator/subagent split was preserved: named briefs handled every non-trivial leaf scope, the main agent validated/aggregated returns, and any inline fallback is explicitly marked `subagent-runtime-unavailable`.
- [ ] Every EF widget's prop names came from the committed SSOT `cli/src/generated/widget-schemas.json` (or the live `wpdev elementor:schema <site> <widget>` fallback), not memory.
- [ ] Every `ts-*` widget setting shape came from a complete atomic reference fixture under `../../examples/` (created/refreshed via `wpdev elementor:dump <site> <widget> --post <real_id>`), not memory or an ad-hoc live copy.
- [ ] Widget JSON was constructed by parallel subagents, one per node — see [`parallel-dispatch.md`](parallel-dispatch.md).
- [ ] No single `ef-card` wrapped in a container at root (`wpdev elementor:strip:wrappers <site>` would flag it; `--fix` removes the wrapper).
- [ ] CPT-template strings use Voxel dynamic tags wrapped in `@tags()...@endtags()`; vx envelopes used for `_cssid` and image refs.
- [ ] Form/feed connection IDs (`ts_post_to_feed`, `connect_map`, `ts_card_template__<type>`) are valid post IDs on the target site.
- [ ] `wpdev elementor:lint <site> --post <id>` passes with zero `unknown-prop` / `type-mismatch` findings.
- [ ] Before any non-trivial template modification, `wpdev elementor:revisions:prune <site> --post <id>` ran unconditionally (snapshot, then delete all revisions) so the build targeted the latest `_elementor_data`.
- [ ] `wpdev elementor:codegen` ran at the start of the run (regenerated the schema SSOT and synced it into `references/ef/widget-schemas.json`).
- [ ] After write, the template was opened and saved in the Elementor editor (regenerates CSS/JS).
- [ ] Browser verification: a representative sample of real posts (one is never enough) navigated via the `agent-browser` CLI (unique `--session` each), every post returning Pass on selector-found / no-console-errors / no-page-errors / no-tag-leakage / expected-text-rendered / **layout assertions** (section width, grid tracks, inherited `--ef-cols`, hero tag) / screenshot-read — per [`browser.md`](../verification/browser.md). A `render-unverified` flag (browser unavailable) is NOT a pass.
- [ ] `wpdev rebuild <site> --only purge` (or full `wpdev rebuild <site>`) ran post-write so LiteSpeed serves the new CSS.
- [ ] Every raw wp-cli call used the cwd-independent `wpdev wp <site> <subcommand>` passthrough — **never** `cd sites/<site> && wp …` (the Bash tool persists cwd across calls, so the 2nd relative `cd sites/<site>` in a session fails `no such file or directory`). SSOT: [`wpdev-ops.md`](wpdev-ops.md) §WP-CLI passthrough. (`sites/<site>/…` as a plain path argument to `tail`/`cat`/`Read` is fine — the ban is on `cd`-ing into the site dir.)
